# 01 — Apply migration 008 and add Playwright to the environment

**What to build:** After this ticket, the `products` table exists in the production database and the production image can render pages with a headless browser. Concretely: `alembic upgrade head` has been run against production so `products` (and its `product_type` enum) is live, and `playwright` + a bundled Chromium + its system libraries ship in the production image so any code that later calls `playwright.sync_api` renders on the server instead of crashing on a missing browser. This is the prefactoring for the whole sync: nothing can write to `products` or render on the server until it lands. No sync logic, endpoint, cron loop, or sync module is built here.

**Blocked by:** None — can start immediately

**Spec:** [spec.md](./spec.md)

**Status:** ready-for-agent

## Context

Everything below was confirmed in the repo — use it, don't re-derive it.

**Migrations run manually via Alembic — there is no auto-migrate on deploy.** The Dockerfile copies `migrations/` and `alembic.ini` into the image but the container's `CMD` only starts `uvicorn`; nothing runs `alembic upgrade` on boot, and neither `docker-compose.yml` nor CI does either. So applying the migration is an explicit, separate step you run by hand: `poetry run alembic upgrade head` from the repo root.

**Alembic reads `DATABASE_URL` from app settings.** `migrations/env.py` does `config.set_main_option("sqlalchemy.url", settings.database_url)` — `sqlalchemy.url` in `alembic.ini` is intentionally empty. `settings.database_url` (`app/config.py`) is loaded from the environment / `.env`. So the DB Alembic touches is whatever `DATABASE_URL` points to when you run the command.

**The local `.env` points `DATABASE_URL` at PRODUCTION (Neon).** `.env` has `DATABASE_URL=postgresql+asyncpg://neondb_owner:...@ep-fragrant-frost-aurhemzs-pooler...neon.tech/neondb?ssl=require` (the commented-out "Supabase" line above it is stale — the provider is Neon). `docker-compose.yml` uses the same Neon URL. **Running `alembic upgrade head` locally writes directly to production.** That is the intended way to apply this migration — there is no separate prod shell — but it means the run is not a dry-run: it is the production change. The migration's `upgrade()` guards on `information_schema.tables` and returns early if `products` already exists, so it is idempotent and safe to re-run.

**Migration 008 already exists.** `migrations/versions/20260302_000004_008_add_products_table.py`, revision `008`, revises `007`. It creates the `product_type` enum (`sinuca`, `fitness`) and the `products` table with the unique constraint `uq_products_company_type_wp` on `(company_id, type, wpId, isMotherCategory)`. The `Product` ORM model is already in `app/models/tables.py`. This ticket only *applies* it.

**Playwright is nowhere in the project yet.** Not in `pyproject.toml` `[tool.poetry.dependencies]`, not in the Dockerfile, not in any requirements file. `experimental-tools/render_novos.py` imports `playwright.sync_api` and hard-codes a macOS-only Chromium path (`~/Library/Caches/ms-playwright/chromium-1234/...`, a placeholder) — that path is local-dev only and does not carry to the container. There is **no pinned Playwright version anywhere**, so you choose the version; pin `playwright` in `pyproject.toml` and let `playwright install chromium` fetch the Chromium build that matches that exact library version (never a distro/apt Chromium — Playwright only drives its own build).

**Dockerfile today.** `FROM python:3.11-slim`; apt-installs `gcc curl postgresql-client`; `pip install poetry==1.7.1`; `poetry config virtualenvs.create false`; `poetry install --only main`. It installs no browser and none of the shared libs a headless Chromium needs (libnss3, libnspr4, libatk, libgbm, libxkbcommon, fonts, etc.).

**Lock / Poetry version gotcha — read before touching deps.** `poetry.lock` is `@generated by Poetry 2.3.1` (the version on the local machine), but the **Dockerfile pins Poetry 1.7.1**. Poetry 1.7.1 cannot read a 2.x-format lock, so the VPS build (`docker build` → `poetry install`) is already on a collision course; adding a dep and re-running `poetry lock` (with local Poetry 2.3.1) regenerates the 2.x lock and 1.7.1 in the image will reject it. Bump the Dockerfile's Poetry to a 2.x line matching what generates the lock, so image and lock agree. There is **no active CI lock check** — `.github/workflows/deploy.yml` is disabled (`workflow_dispatch` only) and the real deploy is a build-on-VPS from an FTP-shipped package — but the VPS `poetry install` still fails on a lock out of sync with `pyproject.toml`, so the lock must be committed in step with the pyproject change.

## Tasks

**1. Apply migration 008 to production**

- [ ] Run `poetry run alembic upgrade head` from the repo root with the local `.env` in place (so `DATABASE_URL` = Neon prod). This creates `products` + the `product_type` enum in production.
- [ ] Confirm it landed: query production for the `products` table and the `uq_products_company_type_wp` constraint (e.g. `\d products` via `psql`). For a libpq client, convert the URL: `postgresql+asyncpg://`→`postgresql://` and `?ssl=require`→`?sslmode=require`.
- [ ] Confirm idempotency by running `alembic upgrade head` a second time — it must be a no-op (the `information_schema.tables` guard returns early), leaving the schema unchanged.

**2. Add Playwright + Chromium to the production image**

- [ ] Add `playwright` (pinned to a concrete version) to `[tool.poetry.dependencies]` in `pyproject.toml` — it is a **production** dependency, not a dev one, because the server renders new products.
- [ ] Regenerate `poetry.lock` (`poetry lock`) and commit it together with the `pyproject.toml` change so the VPS `poetry install` stays consistent.
- [ ] Bump the Dockerfile's `poetry==1.7.1` to a 2.x version that matches the Poetry generating the lock (currently 2.3.1), so the image's Poetry can read the committed lock.
- [ ] In the Dockerfile, after `poetry install --only main`, install the browser and its OS libs. Use Playwright's own tooling — `playwright install --with-deps chromium` (or `playwright install-deps` + `playwright install chromium`) — so the Chromium build matches the pinned library version. Do not apt-install a distro Chromium.
- [ ] Point Playwright's browser cache at a fixed in-image location (set `PLAYWRIGHT_BROWSERS_PATH`) so the browser installed at build time is the one found at runtime, independent of `$HOME`. Add a one-line `# ...` comment only for the non-obvious *why* (build-time vs runtime cache path), nothing that restates the command.

**3. Verify the image renders**

- [ ] Build the image locally and confirm inside the container that `python -c "from playwright.sync_api import sync_playwright; ..."` can launch headless Chromium and load a page (no missing-shared-library error). This proves the OS libs and the browser are both present.

## Acceptance criteria

- [ ] `products` table and `product_type` enum exist in the production Neon database, with the `uq_products_company_type_wp` unique constraint; re-running `alembic upgrade head` is a clean no-op.
- [ ] `playwright` is listed under `[tool.poetry.dependencies]` (production) with a pinned version, and `poetry.lock` is regenerated and committed in the same change.
- [ ] The built production image launches headless Chromium successfully from inside the container (browser binary + all required OS libs present); the Dockerfile's Poetry version can read the committed lock.
